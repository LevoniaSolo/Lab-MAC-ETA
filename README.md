# Лабораторная работа № 2 — исследование механизмов распределения задач

Версия 2. Python **3.10+**, только стандартная библиотека. Реализована виртуальная МАС из принятой ЛР №1: клиент G, координатор C, вычислительные агенты W1–W4. Ресурсы узлов: (4 CPU, 8 ГБ), (8, 16), (12, 16), (6, 32). Узлы могут одновременно выполнять несколько задач, если хватает CPU и RAM.

## Запуск (Ubuntu / VS Code)

```bash
python3 main.py
python3 main.py --mode central --count 10 --verbose
python3 main.py --mode cnp --count 10 --verbose
python3 -m unittest -v
```

`python3 main.py` проводит три серии экспериментов (низкая, средняя, высокая нагрузка; по 3 одинаковых seed для каждого механизма). Результаты — `results/metrics.csv`. При запуске с `--mode central` или `--mode cnp` сохраняются также `results/<mode>_messages.csv` и `results/<mode>_events.txt`.

Можно менять параметры:

```bash
python3 main.py --mode compare --count 40 --seed 11 --capacity 5 --parallel 4
python3 main.py --mode cnp --count 10 --interval 1 --capacity 2 --verbose
```

`--capacity` — **общий бюджет координатора на обработку входящих и отправку исходящих сообщений за один такт** (по умолчанию 5); `--parallel` — максимальное число одновременно ведущихся переговоров о назначении (по умолчанию 4). Эти параметры **одинаковы для обоих алгоритмов**.

## Файлы

- `models.py` — структуры задания, сообщения, конфигурации узлов.
- `agents.py` — клиент, координатор, автономный исполнитель, эвристики выбора.
- `simulation.py` — доставка сообщений, ограниченная пропускная способность координатора, параллельные переговоры, выполнение задач, метрики.
- `experiments.py` — воспроизводимая нагрузка, повторные прогоны, CSV.
- `main.py` — интерфейс командной строки.
- `test_simulation.py` — автоматические проверки.

## Сравниваемые протоколы

**Централизованный:** `STATUS_REQUEST` → `STATUS_RESPONSE` → выбор по актуальной полученной информации → `TASK_OFFER` → `TASK_ACCEPT`/`TASK_REJECT`.

**CNP:** `CFP` → `PROPOSAL`/`TASK_REJECT` → выбор → `TASK_OFFER` победителю и `PROPOSAL_REJECT` остальным участникам → `TASK_ACCEPT`/`TASK_REJECT`.

Каждый исполнитель самостоятельно проверяет ресурсы при окончательном принятии задания. Оба режима используют одну и ту же оценку: минимальная средняя прогнозируемая загрузка L, при равенстве — минимальный **модуль** остаточного дисбаланса B, затем ID исполнителя. Реализация не использует готовых алгоритмов распределения из сторонних MAS-библиотек.

## Последние изменения

1. Каждое отправленное сообщение доставляется адресату **на следующем такте**.
2. Координатор обрабатывает ограниченное число входящих **и исходящих** сообщений за такт (`--capacity`). Это модель накладных расходов на координацию, а не физическая сеть.
3. Координатор может вести до `--parallel` переговоров одновременно. Назначения не обязаны выполняться строго последовательно.
4. Дополнительные уведомления `PROPOSAL_REJECT` в CNP занимают часть того же бюджета сообщений и при нагрузке могут увеличивать время ожидания. Различие времени **не задаётся искусственно для CNP**: оба режима работают с одинаковыми ограничениями.
5. Если все узлы временно заняты или окончательная проверка отклонила назначение, задача возвращается к повторной попытке. Невыполнимые даже на свободном узле задачи отклоняются до запуска симуляции с явной ошибкой.

## Определения метрик

- `makespan`: такт **получения клиентом последнего результата**, начиная с такта 0. Это полное время обслуживания набора запросов, включая обратную доставку результата; не только время вычисления.
- `avg_wait`: среднее `started_at - arrival` для успешно выполненных задач (ожидание и координация до старта).
- `avg_response`: среднее `finished_at - arrival` (до завершения вычислений на узле, **без** обратной доставки результата).
- `messages_total`: число **отправленных** сообщений всех типов.
- `messages_coordination`: число отправленных сообщений назначения: `STATUS_REQUEST`, `STATUS_RESPONSE`, `CFP`, `PROPOSAL`, `PROPOSAL_REJECT`, `TASK_OFFER`, `TASK_ACCEPT`, `TASK_REJECT`.
- `coordination_ticks`: сумма по задачам интервалов от начала первой попытки согласования до получения координатором `TASK_ACCEPT` (включает ожидание в очередях сообщений и повторные попытки). Это **не** число уникальных тактов занятости координатора: переговоры идут параллельно.
- `avg_coordination_ticks`: `coordination_ticks / число завершённых задач`.
- `cpu_utilization` / `ram_utilization`: средняя занятость ресурсов всех узлов за весь горизонт симуляции.
- `deadline_met`: число задач, вычисления которых завершились не позже их срока.

Задания генерируются с фиксированными seed и в обоих режимах абсолютно одинаковы. Результаты могут совпадать при низкой нагрузке — это допустимо. Сравнивать следует **время, сообщения и ожидание**, а не пытаться обязательно получить различие по каждой метрике.

## Ограничения модели

Симуляция дискретная, задания не выполняют реальных вычислений, CPU и RAM — условные ресурсы. Задержка доставки любого сообщения составляет один такт. Исполнители обрабатывают входящие сообщения без отдельного ограничения пропускной способности; ограничен именно координатор. Нет реальных сетевых сбоев, потери сообщений или злоумышленников — они относятся к ЛР №4. Время обработки сообщений — проектное допущение, которое необходимо описать в отчёте ЛР №2.
